02 / LOCATIONS

配置到底存在哪里

位置作用修改后如何生效
项目根目录 .env本地真实配置；Next.js Web 自动读取，Worker / 脚本通过命令的 --env-file=.env 读取。重新启动受影响的 Web 或 Worker。
.env.example本地模板，允许提交 Git；只放示例和空密钥。修改模板不会改变正在运行的服务。
服务器 /etc/sharing/lightsail.env生产真实配置，由 Compose 的 --env-file 载入；位于仓库外。运行对应服务的 dc up -d --wait，按变化重建容器。
deploy/lightsail/.env.example生产模板，包含域名、镜像标签、数据库密码和各 API 凭据。仅首次创建配置时复制；后续直接编辑真实文件。
src/server/env.ts校验格式、默认值、地址一致性与必填项。修改代码后，生产需要构建并部署新镜像。
src/server/auth-options.tsGoogle 登录、公司身份限制、MCP OAuth 插件配置。修改代码后重启本地 Web；生产重新构建部署。
Google / AWS / GitHub 后台OAuth 回调、API 启用、计费、权限、DNS 和 Deploy key 等平台侧设置。平台保存后生效或等待传播；本地仍需填入匹配的配置。

Web 的环境变量加载优先级：进程环境 → .env.$NODE_ENV.local → .env.local（测试除外）→ .env.$NODE_ENV → .env。项目的 Worker 命令只显式加载根目录 .env，不会自动采用 Next.js 的整套加载优先级。

配置密钥时保持服务端变量名，不添加 NEXT_PUBLIC_ 前缀。不要把真实 .env、API Key、数据库备份或完整 Compose 配置输出放进 Git、HTML 文档或 Plugin 分发包。

项目配置读取入口：src/server/config.ts（Web）与 src/server/worker-config.ts（Worker）。

03 / GOOGLE OAUTH

配置 Google 登录

目标：让已验证的公司 Google 账号登录 Sharing。项目当前公司邮箱域名为 authright.com。

平台入口 Google Auth Platform → Clients · Branding · Audience · Data Access

  1. 选择正确的 Google Cloud 项目。已有配置时，在 Clients 中查找与本地 GOOGLE_CLIENT_ID 相同的客户端。仓库没有记录实际 Cloud 项目名称、项目 ID 或 OAuth 客户端名称，需要在后台确认。
  2. 填写 Branding。设置应用名称（例如 Sharing）、支持邮箱、联系信息；按实际应用补充主页、隐私政策和相关域名。
  3. 设置 Audience。项目方案使用 Internal，供所属 Google Workspace / Cloud Identity 组织使用。Internal 需要组织条件支持；若后台只有 External，先核对项目所属组织。External 的测试用户在 Audience 中管理。
  4. 创建或编辑 Web application 客户端。在 Clients 选择 Web application，按下面表格填写 origin 和回调。
  5. 保存 Client ID / Secret。写入本地 .env 或生产 /etc/sharing/lightsail.env。新建 Secret 时及时保存；以后台当前可用的密钥管理方式为准。
  6. 确认权限。网页登录只需 openid email profile 基本身份权限，Data Access 中核对这些范围。
设置本地开发生产环境

上表 origin 遵循仓库配置手册；本项目核心为服务端 OAuth 回调，Redirect URI 必须与实际请求逐字匹配。本地用 localhost 登录，避免与 127.0.0.1 混用。开发与生产宜采用独立凭据。

公司成员如何加入

代码检查 emailVerified === true，并要求邮箱后缀与 GOOGLE_WORKSPACE_DOMAIN 一致。符合条件的公司用户首次登录自动成为普通成员；初始化管理员只授予管理员角色。现有实现不要求邀请或手工批准。

代码：src/server/auth-options.ts、src/server/company-identity.ts、src/app/sign-in/sign-in-button.tsx。认证路由：src/app/api/auth/[...all]/route.ts。

04 / GEMINI API

配置 Gemini 摘要服务

项目使用 Gemini Developer API 的 REST 接口。文章和视频摘要都由 Worker 生成，每次处理通常调用一次模型。

平台入口 Google AI Studio → API Keys · Google Cloud → Billing

  1. 选择或导入 Cloud 项目。进入 AI Studio，接受所需条款，在 Dashboard → Projects 中确认项目；已有 Cloud 项目可通过 Import projects 导入。
  2. 创建 API Key。在 API Keys 中选择目标项目创建并保存密钥。遇到权限不足时，由项目管理员核对创建 API Key、启用服务及关联服务账号所需权限。
  3. 核对 API 与密钥限制。当前官方文档说明 AI Studio 新建 Key 使用 authorization key，默认限制为 Gemini API；旧 standard key 需要明确限制。若旧密钥显示 Unrestricted，按 AI Studio 提示限制为 Gemini API。接口访问失败时核对 Generative Language API 和密钥权限。
  4. 核对实际计费档位。在 AI Studio 项目 / Key 页面及 Cloud Billing 确認实际使用 Free 或 Paid；付费方案按平台引导完成关联计费与当前付款设置。
  5. 填入项目配置。将 Key 写入 GEMINI_API_KEY，把实际档位同步为 GEMINI_BILLING_TIER=free 或 paid。
  6. 同时完成 YouTube Key 配置后启用处理。设 CONTENT_PROCESSING_ENABLED=true，启动或重新创建 Worker，提交一个样本验证摘要。
GEMINI_API_KEY=YOUR_GEMINI_API_KEY
GEMINI_BILLING_TIER=free
YOUTUBE_API_KEY=YOUR_YOUTUBE_API_KEY
CONTENT_PROCESSING_ENABLED=true
WORKER_CONCURRENCY=2
SUMMARY_CONCURRENCY=1
档位设置与费用：GEMINI_BILLING_TIER 仅决定 Sharing 使用哪套费用估算；它不会修改 Google 平台的计费档位、账单或额度。Free 模式显示的零估算成本也不是供应商账单凭证。实际用量、价格和配额以对应 Cloud 项目为准。

模型在哪里配置

当前代码固定模型为 gemini-3.5-flash-lite，常量 GEMINI_SUMMARY_MODEL 位于 src/server/content/gemini.ts。当前没有 GEMINI_MODEL 环境变量；切换模型需要修改代码，核对输出结构、模型可用性与费用估算，再验证并重新构建生产镜像。

Worker 如何启动

# 本地：另开终端，项目根目录执行
pnpm dev:worker

# 本地已构建版本
pnpm start:worker

# 生产：先按第 08 节定义 dc，再重新加载 Worker 配置
dc up -d --wait worker
dc logs --tail=100 worker

pnpm dev 只启动网页。Worker 在进程启动时读取开关；设为 true 后会处理已有排队链接。启动日志应出现 worker_ready、contentConsumption: enabled，并持续输出 worker_heartbeat。

当前视频方案把公开 YouTube URL 直接交给 Gemini，非流式请求最长 600 秒；时长至少 30 分钟或未知时使用 0.1 fps。当前流程不需要 yt-dlp、FFmpeg、下载代理或 Files API。查询已有分享不会调用模型。

代码：src/server/content/gemini.ts、src/worker/index.ts、src/server/env.ts。说明：当前视频 Worker 文档（文件名保留历史命名）。

平台依据：API Key 创建、项目与限制计费配置请求限额当前价格
05 / YOUTUBE DATA API

配置 YouTube 视频元数据

YouTube Data API v3 读取公开视频的标题、Description、时长等；视频内容摘要由上一节的 Gemini 生成。

平台入口 API Library → YouTube Data API v3 · APIs & Services → Credentials

  1. 选择用于 YouTube 的 Cloud 项目，在 API Library 搜索 YouTube Data API v3 并启用。
  2. 进入 Credentials → Create credentials → API key，创建 Key。
  3. 编辑该 Key，将 API restrictions 限制为 YouTube Data API v3。这是 Worker 服务端调用，不采用网页 HTTP referrer 限制；如设置 IP 限制，填写实际服务器出口 IP 并验证。
  4. 把密钥写入 YOUTUBE_API_KEY，重启本地 Worker 或重建生产 Worker 容器。
  5. 提交一个公开视频，确认详情页元数据与摘要都生成成功；配额在对应 API 的 Quotas / Metrics 中核对。
YOUTUBE_API_KEY=YOUR_YOUTUBE_DATA_API_KEY

当前 Worker 只要启用内容处理，就要求 Gemini 与 YouTube 两个 Key 同时存在，即使先只测试文章也需要填齐。建议各服务采用独立 Key，便于限制权限、排查和轮换。

代码：src/server/content/youtube.ts、src/worker/index.ts。

平台依据：YouTube API 凭据创建
06 / DATABASE & IDENTITY

数据库、签名密钥与初始管理员

本地首次搭建

开发工具要求：Node.js 24、pnpm 11.25.0 和 Docker。以下命令在项目根目录执行；已有 .env 时直接编辑，不覆盖现有文件。

pnpm install --frozen-lockfile
# 仅首次搭建且 .env 不存在时复制
cp .env.example .env

# 每次生成一个独立随机值，分别填两个签名密钥
openssl rand -hex 32
openssl rand -hex 32

# 填齐 Web 配置后初始化数据库与管理员
docker compose up -d --wait
pnpm db:migrate
pnpm admin:bootstrap tao.xu@authright.com
pnpm dev
字段配置方法
DATABASE_URL本地模板：postgresql://sharing:sharing_local@127.0.0.1:55432/sharing。本地 Docker 只绑定 loopback 的 55432 端口。
TEST_DATABASE_URL独立测试库：postgresql://sharing:sharing_local@127.0.0.1:55432/sharing_test。集成测试不使用正式业务库。
BETTER_AUTH_SECRET至少 32 字符，使用随机生成值；服务于 Better Auth 认证。
CURSOR_SIGNING_SECRET另一份独立随机值，至少 32 字符；用于列表分页游标签名，变量名中的 CURSOR 与 Cursor 编辑器无关。

两个签名密钥必须不同。管理员初始化要在目标邮箱首次登录前执行；如果该邮箱已经是普通成员，脚本会拒绝自动提升，需由现有管理员通过成员管理页调整角色。

生产数据库

生产 PostgreSQL 在 Compose 内部网络中，连接地址使用 postgres:5432。POSTGRES_PASSWORD 与 DATABASE_URL 中的密码必须一致；采用随机 hex 密码可减少 URL 转义问题。已有数据卷的数据库密码不会因为修改环境变量自动更新。

本地定义：compose.yaml；生产定义：deploy/lightsail/compose.yaml；管理员入口：scripts/bootstrap.ts、src/server/bootstrap.ts。

07 / MCP OAUTH

连接客户端并授权访问 Sharing

Sharing 自己运行 OAuth 授权服务，代码入口为 src/server/auth-options.ts 的 mcp({...}) 插件。登录页是 /sign-in，授权确认页是 /consent，资源地址来自 MCP_RESOURCE_URL。客户端可以动态注册，用户仍需登录并同意授权。

权限用途
shares:read读取分享列表与详情。
shares:write提交分享、撤回本人分享。
members:read搜索团队成员。
offline_access客户端需要维持连接时申请刷新令牌。

Codex、Claude Code 与 Cursor Plugin 当前版本为 0.4.0，默认连接生产 MCP。安装与更新方法见 独立插件仓库 README；用户电脑不需要运行本地 Web、Worker 或数据库。

  1. 安装并启用插件，确认 MCP 地址为 https://sharing.authright.com/mcp；只有开发调试才使用本地服务。
  2. 发起 OAuth 登录；浏览器中使用目标公司 Google 账号登录 Sharing。
  3. 在授权页核对账号和所需权限，选择 Allow access。
  4. 实际调用 list_shares 验证读取；需要写入时再确认相关权限。

本地 Codex 配置示例，可合并到客户端配置中；正式连接将 URL 替换为正式地址：

[mcp_servers.sharing-local]
url = "http://localhost:3000/mcp"

Cursor 的 http://localhost:8787/callback、http://127.0.0.1:8787/callback 是客户端接收 Sharing 授权码的地址，服务端已部署兼容修复。它们不需要填入 Google Web OAuth 客户端；Google 只登记本项目 /api/auth/callback/google 回调。

其他 MCP 客户端填写相同服务地址，注册与登录方式按客户端支持情况执行。仅修改 URL 不能证明已完成授权；需要完成浏览器确认并成功调用工具。

授权身份取自点击 Allow access 时的 Sharing 网页账号。切换网页账号不会改变已有客户端连接的身份；在账户设置撤销旧连接，再用目标账号重新授权。撤权保留网页登录，但旧客户端令牌失效。

发现端点：/.well-known/oauth-protected-resource/mcp 与 /.well-known/oauth-authorization-server/api/auth；OAuth 端点挂载在 /api/auth/*。

权限：src/server/mcp-scopes.ts；授权记录：src/server/oauth-grants.ts；客户端本地示例：codex-config.toml。

08 / PRODUCTION

域名、服务器与生产配置

当前部署方案：AWS Lightsail 上运行 Caddy、Web、Worker 和 PostgreSQL。仓库最近部署记录使用域名 sharing.authright.com；本文不重复生产状态验收。

平台入口 AWS Lightsail · 域名所在的 DNS 管理平台 · GitHub 仓库 Deploy keys

  1. Lightsail：创建 Ubuntu 实例，绑定 Static IP；网络防火墙开放 80 / 443，SSH 22 限制到管理员 IP。
  2. DNS：将正式子域名的 A 记录指向该 Static IP；IPv6 配置完整后再发布相应 AAAA 记录。
  3. GitHub：生成服务器专用 SSH 密钥，将公钥登记为只读 Deploy key，私钥保留在服务器；项目路径按部署手册为 /opt/sharing。
  4. Google：在生产 OAuth 客户端登记正式 HTTPS origin 与 /api/auth/callback/google 回调。
  5. 生产配置：首次把生产模板复制为 /etc/sharing/lightsail.env，文件权限为 600；用 sudoedit 填入独立生产凭据。
  6. 构建与启动：按部署手册构建 Git SHA 镜像，填写 SHARING_IMAGE，初始化数据库、运行迁移、初始化管理员，再启动 Web / Worker / Caddy。
# 在 Lightsail 的 SSH 终端定义；每次新会话重新定义
dc() {
  sudo docker compose --env-file /etc/sharing/lightsail.env \
    -f /opt/sharing/deploy/lightsail/compose.yaml "$@"
}

# 编辑现有生产配置
sudoedit /etc/sharing/lightsail.env
dc config --quiet

# 仅更新运行配置时，重新加载受影响的服务
dc up -d --wait web worker caddy
dc ps

GOOGLE_CLIENT_ID=YOUR_PRODUCTION_GOOGLE_CLIENT_ID
GOOGLE_CLIENT_SECRET=YOUR_PRODUCTION_GOOGLE_CLIENT_SECRET

GEMINI_API_KEY=YOUR_GEMINI_API_KEY

上述 dc up 用于加载运行配置，不会自动拉取源码、构建镜像或执行迁移。代码更新走完整部署流程，先备份再迁移。Docker 持久卷保存运行数据，但日常还需要异机数据库备份。

Cursor 点击授权不打开浏览器

先查看 MCP 日志。若出现 web clients require https redirect URIs on non-loopback hosts，错误发生在注册阶段。生产 Web 5b97020 已补齐旧 cursor 协议及 localhost/IPv4 注册兼容；执行 Developer: Reload Window，再从 Sharing 连接授权。连续重试后的 429 是限流，暂停点击、等窗口结束再试。浏览器打开与登录回跳仍需要实际验证。

Google 报 redirect_uri_mismatch

检查正确 Cloud 项目下正确 OAuth 客户端的 Redirect URI。协议、域名、端口、路径必须匹配；本地回调是 http://localhost:3000/api/auth/callback/google。同时检查 APP_URL，保存后重新发起登录。

Google 登录后提示无访问权限

检查邮箱已验证且属于配置的公司域名；Google Audience 也可能限制登录。首次登录自动创建普通成员，bootstrap 管理的是初始管理员角色。

内容一直 queued / 排队中

确认 Worker 正在运行、内容处理开关为 true、两个 API Key 已填且 billing tier 正确。修改 .env 后重启 Worker；生产通过 dc up 重新加载环境。网页正常并不能证明 Worker 正在消费队列。

Gemini 或 YouTube 返回 400 / 401 / 403

依据对应 API 的错误检查 Key、项目、启用服务、Key 限制与权限。Gemini 的模型及输入兼容性也需核对；后台 Key 限制若按网页 referrer 配置，可能与 Worker 服务端请求不匹配。

Gemini 返回 429 / 额度不足

检查对应 Cloud 项目的额度、计费和当前用量，降低摘要并发或等待额度恢复。当前 Worker 将 Gemini 429 记录为处理失败，保留分享；容量恢复后可手动重试。SUMMARY_CONCURRENCY 限制并发数，不是 RPM / TPM / RPD 调度器。

MCP 返回 401 / invalid_grant

未授权请求返回 401 属于正常认证挑战。已授权请求则检查连接是否撤销、令牌是否失效、资源地址和权限是否正确；在客户端重新发起 OAuth。撤销后旧访问与刷新令牌继续失效。

修改生产配置后似乎没有变化

核对编辑的是 /etc/sharing/lightsail.env，执行的 Compose 使用了正确 --env-file 与 -f 路径。环境变量变更用 dc up 重建受影响的容器；普通 restart 不会重新注入新配置。代码变化还需要重新构建并部署镜像。

生产 Caddy 502 / HTTPS 不可用

HTTPS 问题先查 DNS、Static IP、防火墙和 Caddy 日志；502 再查 Web 健康、数据库连接、迁移与启动配置。完整操作参见部署手册。
